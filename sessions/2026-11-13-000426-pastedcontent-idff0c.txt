● The system works end to end. I tested it on anthropic.com: it found the
  /company/leadership page and the Wikipedia article, stored 25 leader records
  with source URLs in SQLite, and answered questions in the Streamlit chat with
  cited sources. No errors came up in the app test.

  To run it: streamlit run app.py, enter a URL in the sidebar, click Collect,
  then ask questions.

  What each file does
  - scraper.py finds and fetches the pages:
    - It checks robots.txt, then ranks links on the homepage by leadership
      keywords (leadership, executive, team, board…). It also tries common paths
      like /about/leadership and follows one more level of links.
    - It skips blog, news, research and careers sections, and pages that
      redirect to another domain.
    - It also pulls the company's Wikipedia infobox, but only if the article
      links back to the company's domain.
  - rag.py does the Gemini work:
    - Collecting: Gemini pulls name, title, department and seniority out of each
      page in a fixed structured format. A person is kept only if their name
      appears word for word on the page, which guards against made-up names. The
      source URL is attached by the code, not by the model, so citations always
      point to a page that was really fetched.
    - Answering: the prompt gets the full leadership table plus the stored page
      excerpts that best match the question by keyword. Gemini has to answer
      only from that and cite URLs.
  - database.py has three SQLite tables: companies, leaders (each with a
    source_url) and sources (the raw page text). Collecting a company again
    replaces its old data.
  - app.py is the Streamlit app: a sidebar to collect or pick a company, a
    leadership table with clickable source links, and the chat.
  - I also filled in requirements.txt and README.md, which covers the design
    choices and limitations, and added leadership.db to .gitignore.

  Problems I hit while testing
  - Gemini model: gemini-2.5-flash is no longer offered to new users.
    gemini-3.8-flash kept returning 503 (overloaded), and the SDK retried it
    quietly until the run hung. The default is now gemini-3.5-flash. Calls have
    a 60s timeout and switch to other models automatically on 503/429 errors.
    You can change the model with GEMINI_MODEL in .env.
  - Duplicate people: someone who appears on both the company site and Wikipedia
    gets two rows, one per source. I kept it that way so each fact has its own
    citation, and the answers already merge them correctly. The table header
    shows both counts ("N people, M sourced records").

  Limitations for your write-up (also in the README)
  - Team pages built with JavaScript, and sites that block bots, won't return
    much. Adding Playwright would fix that.
  - Coverage is limited to the company site and Wikipedia. SEC DEF 14A filings
    and press releases would be the next sources to add.

● Why it fails today

  - meetcampfire.com redirects to campfire.ai. The homepage nav has products,
    customers, careers and blog, but no About, Team or Leadership link, and the
    usual paths (/about, /leadership, /team…) don't return pages. So the crawler
    only reaches product pages.
  - No Wikipedia article links to campfire.ai, so that fallback finds nothing
    either.
  - "Campfire" is a common name, so any search has to be pinned to the domain,
    and every result has to be checked for whether it's really this company.

  Planned changes (small, no hardcoded company data)

  1. New search.py for Tavily discovery. It runs about 6 query templates built
     only from the company name and domain: leadership team; CEO/founder;
     C-suite; VP; head of / director; plus one search limited to the company's
     own site. It asks Tavily for the full page text, removes duplicate URLs,
     and returns the same Page(url, text) objects the crawler already returns.
     Everything after that stays the same.
  2. rag.ingest_company: runs crawl, then Wikipedia, then Tavily. A failed crawl
     is no longer fatal when Tavily is available. Gemini calls run in parallel
     because there are more pages now.
  3. Stricter anti-hallucination checks. Gemini must return an evidence quote
     copied from the page that shows the person's role. A record is kept only if
     the name and that quote both actually appear in the page text. The prompt
     also gets the company's domain and description, and is told to return
     nothing for pages about a different company with the same name.
  4. Deduplication. Records are merged by normalized name ("Mariano-Florentino
     (Tino) Cuéllar" and "Mariano-Florentino Cuéllar" become one person). The
     title from the company's own site is preferred, then the most specific
     title. All source URLs for a person are kept.
  5. SQLite. Same tables, plus two new columns on leaders: source_urls and
     evidence. Existing databases get them added automatically (ALTER TABLE).
     The chat context and the table in the UI show all sources and the evidence
     quote.

● I checked the code and the stored Robinhood data (60 rows). Below is what's
  going wrong and what I propose. I haven't changed any code yet.

  Why the duplicates get stored

  1. The name matching only catches exact matches. _person_key (rag.py) reduces
     a name to its first and last word and requires an exact match. So
     dan≠daniel, bhat≠bhatt, and also vlad≠vladimir: Vlad Tenev and Vladimir
     Tenev are a third duplicate you didn't list. The database constraint
     UNIQUE(company_id, name, title) doesn't catch these either.
  2. The evidence check passes both spellings. "Baiju Bhat" really does appear
     on the Substack page, so the misspelling is grounded on its own page. The
     check confirms a name is on the page; it can't tell that two spellings are
     one person.
  3. There's no idea of current vs. past roles. Each person keeps one title, and
     the prompt tells Gemini to skip former roles, so role history is lost. Old
     pages also win over current ones. Vlad's stored title is "Co-Founder and
     Co-CEO" from an old newsroom post, while the SEC proxy says "Chair of the
     Board and CEO". The same problem shows up as two CFOs (Jason Warnick and
     Shiv Verma) and two Chief Legal Officers (Gallagher and Hoge).
  4. Company subdomains aren't counted as the company's own site. The domain
     check compares investors.robinhood.com to robinhood.com and fails. So the
     official current leadership page isn't preferred, and SEC filings aren't
     ranked as authoritative either.
  5. People count = row count, so duplicates inflate any "how many" answer.

  Proposed changes

  Stage 1: rule-based matching (no LLM, fully testable)
  - Clean names more thoroughly: strip accents, punctuation, honorifics,
    credentials ("CFA", "PhD") and middle initials. A parenthetical nickname
    like "(Tino)" is kept as an alias.
  - Same cleaned first and last name → merge.
  - Common nickname and same surname → merge. This uses a small generic table of
    English nicknames (~40 entries: dan/daniel, vlad/vladimir, bob/robert…). It
    isn't specific to any person.

  Stage 2: Gemini only for unclear pairs
  - A pair counts as unclear when the first names match (directly or via
    nickname) and the surnames are 1–2 letters apart (Bhat/Bhatt), or when one
    first name is just an initial ("D." vs "Daniel").
  - Gemini gets both records with their titles, evidence quotes and sources, and
    returns {same_person, confidence, reason}. It merges only if the answer is
    yes with high confidence. If it says no, isn't sure, or the call fails, the
    records stay separate.
  - Names that are merely similar never merge without this check. "Daniel
    Kelati" and "Daniel Gallagher" are never even compared, because the surnames
    differ too much.

  Role history and current titles
  - Extraction keeps former roles, tagged with status (current/former/unknown)
    and an as_of date (from the page, or Tavily's published_date).
  - Each source gets one of three trust levels, by domain type only:
    a. The company's own domain, including subdomains, plus sec.gov.
    b. News and reference sites.
    c. Data-broker and social sites (LinkedIn, RocketReach, Comparably,
       Crunchbase…).
  - Current title = the non-former record with the highest trust level, newest
    first. An undated page on the company's own site counts as current as of the
    day it was fetched. Every other record goes into the person's role history.

  Database
  - leaders stays at one row per person and gets aliases and status columns.
  - A new role_history table stores title, status, as_of, source_url, trust
    level and evidence for each record.
  - Existing databases are migrated automatically. Old companies need to be
    collected again to get role history.

  Chat
  - The context starts with an explicit count, e.g. "Unique people: 55 (current
    48, former 7)".
  - Each person appears once, with aliases, current title and role history.
  - The prompt says to count people, not sources, and to label former roles as
    former.

  Tests (offline, pytest)
  - Dan/Daniel Gallagher merges in Stage 1, with both names kept as aliases.
  - Baiju Bhat/Bhatt merges when a fake Gemini says "same", and stays separate
